# Spec Kit for SPFx work (state as of 2026-10-06)

## Current state of github/spec-kit and github/spec-kit-copilot

### Takeaway
Spec Kit is very active (v1.1.1 released 2026-10-06; near-daily releases) and has grown from a single SDD flow into a "process toolkit" with three entry points (SDD, bug fix, idea assessment), plus extensions, presets, workflows and bundles. For GitHub Copilot it now installs **skills** under `.github/skills/` by default (`/speckit-specify` etc.), with an opt-in `.agent.md` + `.prompt.md` layout. `github/spec-kit-copilot` is a separate, young companion repo (created 2026-06-29, 16 stars) that mainly targets Copilot CLI / Copilot App, not VS Code chat.

**Processes and commands (current README, v1.1.x)**
- README tagline: "Build with a spec, fix a bug, or assess an idea — with your coding agent." Three independent entry points: SDD (core), Bug fixing (`specify extension add bug`), Idea assessment (`specify extension add assess`). "These are independent entry points, not three mandatory phases." — [spec-kit README](https://github.com/github/spec-kit)
- SDD flow: "Constitution once per project; specify → plan → tasks → implement → converge per feature." Repeat implement → converge until it reports "Converged". Clarify, checklist and analyze are optional quality gates — [spec-kit README](https://github.com/github/spec-kit)
- Command reference — [agentic-sdd reference](https://github.github.io/spec-kit/reference/agentic-sdd.html):
  - `/speckit.constitution`: establish/update project principles.
  - `/speckit.specify`: feature spec (what/why, not tech stack); also maintains `checklists/requirements.md`.
  - `/speckit.clarify`: "Asks up to five targeted questions about underspecified areas of the current spec and encodes your answers back into `spec.md`" (formerly `/quizme`).
  - `/speckit.plan`: technical plan; tech stack/architecture/constraints go here.
  - `/speckit.tasks`: break plan into tasks.
  - `/speckit.analyze`: "read-only cross-artifact consistency and quality analysis across spec.md, plan.md, and tasks.md"; never edits files.
  - `/speckit.checklist`: requirements-quality checklists; `/speckit.implement` reads checklist state as a gate and asks before proceeding if items are unchecked.
  - `/speckit.implement`: executes `tasks.md` in phase/dependency order; can be scoped ("Implement only the Setup and Foundational phases...").
  - `/speckit.converge` (new vs 2025 versions): "append-only: it never edits or deletes code, and its only possible write is adding tasks to tasks.md"; outputs "Converged" or appends a Convergence section.
  - `/speckit.taskstoissues`: optional, now deprecated in core (moved to `github` extension).
- Bug extension: `/speckit-bug-assess` → `/speckit-bug-fix` → `/speckit-bug-test`, reports in `.specify/bugs/<slug>/`, verdict `verified`/`partial`/`failed`. Assess extension: intake → research → define → shape → decide, artifacts in `.specify/assessments/<slug>/` — [spec-kit README](https://github.com/github/spec-kit)
- Customization layers: "Extensions add capabilities, presets adapt existing behavior, workflows automate steps, and bundles package a role-based setup." — [spec-kit README](https://github.com/github/spec-kit). Community catalog has ~190 extension rows, including a "Microsoft 365 Integration" extension that fetches Teams messages, meeting transcripts and SharePoint/OneDrive files as Markdown for spec generation (not an SPFx dev extension) — [community extensions](https://github.com/github/spec-kit/blob/main/docs/community/extensions.md)
- Updating the agent context file (e.g. `.github/copilot-instructions.md`) is now done by an `agent-context` extension (`speckit.agent-context.update`), not core — [spec-kit repo, extensions/agent-context](https://github.com/github/spec-kit/tree/main/extensions/agent-context)
- Git branch-per-feature is optional and lives in a `git` extension: "Git initialization and feature branches are optional and are managed by the git extension." — [existing-projects guide](https://github.github.io/spec-kit/guides/existing-projects.html)

### Inferences
- For VS Code Copilot agent mode, `github/spec-kit` alone (skills in `.github/skills/`) is sufficient; `spec-kit-copilot` adds value mainly for Copilot CLI / Copilot App users and is early-stage (0.x, canvases experimental). It is optional for the user's SPFx scenario.
- The velocity (5 releases in 2 weeks, deprecations, command renames like `/quizme` → clarify, new `converge`) means generated skill files will drift from upstream; a pinned version (`@vX.Y.Z`) and periodic `specify` upgrade is needed to avoid stale prompts in the repo.
- Python 3.11 + uv is an extra toolchain dependency on a Windows work laptop that SPFx otherwise does not need (Node only); corporate proxy/allow-listing may matter.
- Spec Kit adds files to `.github/skills/` (or `.github/agents` + `.github/prompts`) which would sit alongside the harness's own Copilot artifacts in the same repo; namespacing (`speckit-*`) avoids collisions but adds to Copilot's skill list.

## What GitHub itself says about when SDD fits

### Takeaway
GitHub's launch post pitched SDD for greenfield, feature work in existing codebases ("most powerful"), and legacy modernization, without listing where it does not fit. The current docs are more nuanced: start brownfield adoption with one bounded change, do not invent constitution rules, and Spec Kit's own contributors use SDD only for "substantial" features while "small fixes" stay in normal issue/PR flow.

### Cited Findings
- Launch post (2025-09-02, Den Delimarsky): SDD works well for greenfield projects; feature work in existing systems is where it is "most powerful"; and legacy modernization. It notes "advanced context engineering practices might be needed" for existing systems; no explicit "don't use" guidance — [GitHub blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) (older, 2025)
- Brownfield guide: "You do not need to recreate an existing system from specifications"; "Do not make 'document the entire existing system' your first feature"; for the constitution "Do not invent standards merely to fill the constitution template... unrealistic rules create noise instead of useful constraints." The new `spec.md` "defines the change you intend to make, not a retroactive specification of every existing behavior." — [existing-projects guide](https://github.github.io/spec-kit/guides/existing-projects.html)
- Spec Kit's own practice: the contribution guide "asks contributors to test relevant changes with SDD while allowing small fixes to use the normal issue and PR process"; "A separate SDD plan is not required for every issue"; "A small change can stay in an issue and PR, while a bug can move through human-gated assessment, repair, and verification." — [agentic-sdlc guide](https://github.com/github/spec-kit/blob/main/docs/guides/agentic-sdlc.md)
- Large features degrade during `/speckit.implement` due to context exhaustion ("agents can start to lose track of the plan, ignore tasks, or hallucinate — usually right before or after context compaction"); fixes: scope runs to N tasks/phase, delegate `[P]` tasks to sub-agents (Copilot in VS Code supports this), or decompose into a "spec of specs" (which "adds the most overhead") — [complex-features](https://github.com/github/spec-kit/blob/main/docs/concepts/complex-features.md)
- Spec persistence is left to the team: three models (flow-back, flow-forward/immutable, living spec). Flow-back suits teams "small enough to notice and reconcile drift quickly"; "The main risk is silent divergence." Docs cite Böckeler's spec-first / spec-anchored / spec-as-source framing — [spec-persistence](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md)
- VS Code's own docs on the built-in Plan agent: "Use dedicated planning for complex changes spanning multiple project areas or uncertain approaches. For small, well-defined edits, direct implementation is more efficient." — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning) (page dated 2026-09-30)

### Inferences
- By GitHub's own practice, SDD is for "substantial" features; the typical SPFx web-part change (new property-pane option, list column display, bug fix, styling tweak) falls on the "small change stays in issue/PR" side.
- The new bug extension (assess → fix → test) is a lighter Spec Kit entry point that may fit SPFx maintenance better than full SDD, though no practitioner reports on it were found.

### Gaps
- No GitHub statement found that explicitly sizes features (e.g. "under N story points, skip SDD").

## Practitioner experiences and critiques 2025-2026

### Takeaway
Credible hands-on reviews (Thoughtworks/Böckeler, Scott Logic) found Spec Kit heavy for small/medium changes: lots of repetitive Markdown, review time dominating (hours vs minutes), and agents still ignoring instructions. 2026 comparisons consistently rank OpenSpec as lighter and better for brownfield. Most numbers come from 2025 versions that predate `converge`, presets and the bug extension.

### Cited Findings
- **Böckeler (Thoughtworks, on martinfowler.com, 2025-10-15)**, testing on a 3-5 point story (an overview modal on an existing dashboard): "this again felt like overkill for the size of the problem"; "spec-kit created a LOT of markdown files for me to review. They were repetitive, both with each other, and with the code that already existed"; the agent duplicated existing classes despite instructions, a "false sense of control"; "for two of the three tools I tried it also seems to be even more work to introduce them into an existing codebase"; "I could have implemented the feature with 'plain' AI-assisted coding, and I would have felt much more in control." Compared Kiro (lighter but still verbose for small tasks) and Tessl — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) (2025)
- **Scott Logic (2025-11-26)**, measured: feature 1 = 33.5 min agent time + ~3.5 h human review (plan review ~2 h, tasks review ~2 h); 689 LOC vs 2,577 lines of Markdown; feature 2 = 23.5 min agent + ~2 h review, ~300 LOC vs 2,262 lines Markdown; 14 files. The author's normal iterative approach: ~8 min agent + 24 min review/test, ~32 min total, no bugs. Claims "around ten times faster" without SDD; "The fastest path is still iterative prompting and review, not industrialised specification pipelines." — [Scott Logic blog](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html) (single-developer anecdote, 2025)
- **OpenSpec vs Spec Kit (2026-06-03)**: OpenSpec ~4 files per change (delta specs) vs Spec Kit 7+ per feature; Spec Kit review felt like "auditing AI-generated prose rather than designing software"; cites Ran Isenberg's Feb 2026 evaluation: planning 3 h/~$25 (OpenSpec) vs 4 h/~$30 (Spec Kit), implementation ~$70 vs ~$45, overall scores 4.00/5 vs 2.77/5. "Spec-Kit is greenfield-optimized"; OpenSpec delta specs need "no constitution needed upfront." Agent used not stated — [ypyl.github.io](https://ypyl.github.io/programming/2026/06/03/openspec-vs-spec-kit-sdd.html) (secondary; Isenberg's original not verified)
- Other 2026 comparison pieces repeat the same framing (Spec Kit heaviest/most flexible, OpenSpec better for brownfield deltas, BMAD heavier multi-role process) — [codemyspec OpenSpec vs Spec Kit](https://codemyspec.com/blog/openspec-vs-spec-kit), [hiddedesmet.com](https://hiddedesmet.com/speckit-vs-openspec), [Medium: Spec Kit, OpenSpec, BMAD on brownfield](https://medium.com/@mathivananmani/reviving-brownfield-projects-with-ai-a-comparative-look-at-github-spec-kit-openspec-and-bmad-a7bc5116dd9a) (not fetched in full; vendor/blog content, anecdotal)
- Spec Kit now ships an `openspec` extension (v1.0.13, "Added openspec extension (#4765)") — [v1.0.13 release](https://github.com/github/spec-kit/releases/tag/v1.0.13)
- **Cost model change**: GitHub Copilot moved from premium requests to usage-based "GitHub AI Credits" starting 2026-06-01; credits are consumed by model and tokens (input, output, cached). Pro/Pro+ get monthly credits equal to the subscription fee; extra usage must be purchased — [GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/), [roboin.io summary](https://roboin.io/article/en/2026/04/28/github-copilot-moves-to-credit-based-billing/)
- **Lighter built-in alternative**: VS Code's Plan agent is read-only, asks clarifying questions, writes the plan to session memory `/memories/session/plan.md` (not a project file; "Open in Editor" to copy), then "Start Implementation" hands off to Agent mode; models configurable via `chat.planAgent.defaultModel` / `github.copilot.chat.implementAgent.model` — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning). Visual Studio got a similar Plan agent in May 2026 that saves `.copilot/plans/plan-{title}.md` — [Visual Studio blog](https://devblogs.microsoft.com/visualstudio/plan-before-you-build-introducing-the-plan-agent-in-visual-studio/)
- The "reinvented waterfall" critique is common in community discussion (Scott Logic title; HN/Reddit threads) — [Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html); HN/Reddit threads were not fetched directly (anecdotal)

### Inferences
- Under token-based billing, Spec Kit's cost is driven by the Markdown it reads and writes: each phase re-reads spec/plan/tasks/constitution, so per-feature token cost is several times a Plan-agent-then-implement loop. The bigger cost for a small team is human review time (Scott Logic: hours of review vs ~30 min).
- Spec drift is a real maintenance item: Spec Kit leaves persistence to the team, and its own repo gitignores `specs/`. Not keeping the specs ("spec-first", throwaway) removes most of the long-term benefit over a Plan-agent plan.
- For 2 mature SPFx solutions with mostly incremental changes, the evidence points to: (a) instruction files plus the SPFx skill, (b) Plan agent → implement for medium changes, (c) Spec Kit (or OpenSpec deltas) only for a large new web part or a cross-cutting change such as an SPFx 1.2x upgrade.

### Gaps
- No practitioner report found that uses Spec Kit with SPFx or with SharePoint specifically.
- No published measurement of Copilot AI Credit consumption per Spec Kit phase.
- No hands-on reviews found of the newer `converge` command or the bug extension; most critiques predate v1.0.
- Kiro specs and BMAD were covered only through secondary comparisons, not their primary docs.

## SPFx-specific: AI guidance, pitfalls, and existing Copilot instructions/templates

### Takeaway
Microsoft now publishes an official (preview) **SPFx development agent skill** (`SharePoint/spfx-dev-skills`) that covers creating projects, upgrades, React/Fluent UI v9 design, and PnPjs data access. It is version-aware for Heft (≥1.22) vs gulp (≤1.21.1) and installs as `.github/skills/spfx/` for Copilot. This targets the exact pitfalls an agent hits (Node pinning, toolchain, interactive Yeoman, PnPjs setup) and is likely more useful for SPFx than Spec Kit. No Spec Kit preset or extension for SPFx exists.

### Cited Findings
**Official SPFx agent skill**
- "The SPFx development skill gives compatible AI coding agents instructions for common SharePoint Framework (SPFx) development tasks... identify the SPFx version in a project, choose the corresponding Heft or gulp toolchain." It is preview ("Review all generated code and commands"). Covers: create projects (Yeoman generator "in non-interactive mode", checks environment), upgrade (CLI for Microsoft 365 upgrade report), React UI (React, TypeScript, Fluent UI v9, theming, a11y), data access ("Use PnPjs by default"). Install manually: clone the repo and copy `plugins/spfx/skills/spfx` into e.g. `.github/skills`; no marketplace/one-command install. Uses `m365 spfx doctor` to check the environment. Doc dated 2026-08-31 — [Microsoft Learn: SPFx agent skills](https://learn.microsoft.com/en-us/sharepoint/dev/spfx/agent-skills)
- Repo contents (last commit 2026-09-02): `SKILL.md` (28-line router) plus `references/create.md`, `upgrade.md`, `react-design.md`, `pnpjs.md`. `react-design.md` links to a `toolchain.md` that is not present in the repo (broken reference at time of checking) — [SharePoint/spfx-dev-skills](https://github.com/SharePoint/spfx-dev-skills) (cloned 2026-10-06)
- Skill's guidance specifics: if Node is incompatible, try `fnm`/`nvm`, re-run `m365 spfx doctor`, and "stop and tell the user" if it cannot be resolved; production build on Heft = `heft build --production` then `heft package-solution --production`, on gulp = `gulp bundle --ship` then `gulp package-solution --ship`; gulp only "if the user explicitly needs" it (`--use-gulp`); after UI changes "MUST run `npm run build`" then smoke-test (`heft start` / `gulp serve`) — [spfx-dev-skills references/create.md, react-design.md](https://github.com/SharePoint/spfx-dev-skills)
- PnPjs reference: initialize once in `onInit()` with `spfi().using(SPFx(this.context))`; selective imports for tree-shaking; "Use `.select()` and `.top()` to limit payload size; never fetch all fields/rows blindly"; "Match the PnPjs major version to the project's SPFx and TypeScript versions"; Graph permissions via `webApiPermissionRequests` in `package-solution.json` with admin approval. It makes PnPjs the default over `SPHttpClient` "Only use raw SPHttpClient or MSGraphClientV3 when the user explicitly requires it" — [spfx-dev-skills references/pnpjs.md](https://github.com/SharePoint/spfx-dev-skills/blob/main/plugins/spfx/skills/spfx/references/pnpjs.md)
- The skill's update record lists "verified facts (Microsoft Learn, June 2026)": 1.22 generator defaults to Heft with gulp selectable; "1.23: New projects Heft-only"; "1.24+: gulp officially unsupported"; upgrading an existing 1.22 project "May keep gulp; switching to Heft is a dedicated migration, not a normal upgrade"; Heft rig `./config/rig.json` → `@microsoft/spfx-web-build-rig`; `gulp serve` → `heft start`, `--ship` → `--production`; new Heft `dev-deploy` action — [spfx-dev-skills todo.md](https://github.com/SharePoint/spfx-dev-skills/blob/main/todo.md) (secondary record; the 1.23/1.24 gulp claims were not checked against release notes)
- Community alternatives: `sudharsank/spfx-enterprise-skills` ("SPFx enterprise skills for AI editors"), and a 2026-09-15 blog "Your AI Coding Agent Doesn't Know SPFx — Here's the Skill Pack That Fixes It" noting agents had issues "with interactive Yeoman prompts and SPFx conventions" — [spfx-enterprise-skills](https://github.com/sudharsank/spfx-enterprise-skills), [spknowledge.com](https://spknowledge.com/2026/09/15/ai-coding-agent-doesnt-know-spfx-skill-pack-fixes-it/) (search snippets only; not fetched in full)
- SPFx Toolkit (PnP VS Code extension) provides an `@spfx` Copilot Chat participant and language-model tools in agent mode — [SPFx Toolkit](https://pnp.github.io/vscode-viva/) (search snippet)

**Version and toolchain facts**
- Compatibility table (page updated 2026-07-07): SPFx 1.22.0-1.23.2 → Node v22, TypeScript v2.9-v5.8, React v17.0.1; 1.21.x → Node v22, TS 5.3; 1.19-1.20 → Node v18. "The SPFx introduced a significant change to the build toolchain starting with the SPFx v1.22 release. The legacy gulp-based toolchain (legacy) was used from SPFx v1.0 - v1.21.1." Also warns: "Using incompatible React versions can cause silent runtime failures without clear error messages... use the `--save-exact` flag" — [Microsoft Learn: SPFx compatibility](https://learn.microsoft.com/en-us/sharepoint/dev/spfx/compatibility)
- Roadmap (Aug 2026): current GA SPFx 1.23.2 (June 2026); SPFx 1.24 GA targeted October 2026 with Copilot Components GA and **React 18 support** ("the single most requested item"); SPFx 1.25 (Dec 2026/Jan 2027) brings "SPFx CLI general availability... replacing Yeoman generator from this version forward" — [Microsoft 365 Dev blog](https://devblogs.microsoft.com/microsoft365dev/sharepoint-framework-spfx-roadmap-update-august-2026/)

**List view threshold and PnPjs paging**
- PnPjs docs: paging is "based on skip tokens and item ids, something that is hard to guess at runtime"; use the async iterator: `for await (const items of sp.web.lists.getByTitle("BigList").items.top(10)) {...}` ("chunks of up to 5000, if left off returns 100 items per loop") — [PnPjs docs/sp/items.md](https://github.com/pnp/pnpjs/blob/version-4/docs/sp/items.md)
- Older guidance uses `items.getAll()` and stresses indexing filter columns so filtered results stay under 5,000; multi-lookup columns cannot be indexed — [TechNet wiki archive](https://learn.microsoft.com/en-us/archive/technet-wiki/53836.handle-large-list-operations-in-sharepoint-framework-to-avoid-threshold) (older, PnPjs v1/v2 era; `getAll()` is not in current PnPjs item docs, which use the async iterator)

### Inferences
- Common SPFx pitfalls an agent will hit, from the sources above: (1) wrong Node major (must be v22 for 1.21-1.23; v18 for 1.19-1.20); (2) mixing gulp and Heft commands or suggesting `gulp serve` on a 1.22+ project, or silently migrating gulp → Heft during an "upgrade"; (3) bumping React (stays 17.0.1 until 1.24 GA; 1.24 introduces React 18) or installing caret ranges instead of `--save-exact`; (4) interactive Yeoman prompts hanging agent terminals (needs non-interactive flags; Yeoman is being replaced by the SPFx CLI in 1.25); (5) PnPjs: re-creating `spfi` per call, missing side-effect imports, unbounded queries, old `getAll()` patterns from training data, and filters on non-indexed columns hitting the 5,000-item threshold; (6) PnPjs major version mismatched with the project's TypeScript. The user's internal UI component library adds conventions no public skill will cover, so a repo-specific `*.instructions.md` is still needed.
- Microsoft's skill plus a short repo-level `copilot-instructions.md`/`*.instructions.md` (pinned SPFx version, Node 22, gulp-or-Heft per solution, internal UI library rules, PnPjs patterns, `--save-exact`, "do not run deploy/App Catalog steps") covers most of what a Spec Kit constitution would encode for SPFx, at a fraction of the ceremony.
- If the two solutions are below 1.22, the coming 1.24/1.25 changes (React 18, gulp unsupported, Yeoman → SPFx CLI) make an upgrade a candidate for a one-off full spec (Spec Kit or Plan agent with a saved plan), since it is cross-cutting and risky.
