# Put agents on the read path first

Adopt agentic CI/CD on this stack in this order. Start with read-only Copilot custom agents in VS Code that diagnose through MCP servers (TeamCity's built-in MCP or CLI, `kubernetes-mcp-server` in read-only mode, the Argo CD MCP server in read-only mode). Then move one headless Copilot CLI job into TeamCity for build-failure triage and GitOps PR review, with results posted as Bitbucket Code Insights. Agents only ever propose GitOps changes on branches; people merge, sync and touch PROD. The GitHub-native agent products, the Copilot coding agent and GitHub Agentic Workflows (gh-aw), don't work here, because both require GitHub-hosted repos ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). What does work is plain glue: TeamCity's agent interfaces, Copilot CLI's headless mode, and Bitbucket's REST and Code Insights APIs. Your guardrails match what the security research recommends. Every public CI/CD agent exploit from 2025 to 2026 combined untrusted text, credentials and a way to send data out. So your rules belong in server-side RBAC and branch permissions, with Copilot deny lists as a second layer. They can't live in prompts alone. For the two SPFx solutions, stop using Spec Kit for routine changes. Use Microsoft's official SPFx agent skill, a repo instructions file and VS Code's Plan agent, and save Spec Kit for a large cross-cutting change such as the SPFx 1.24/1.25 upgrade. Two unknowns decide much of the design: whether Bitbucket is Cloud or Data Center, and whether TeamCity is 2026.1 or newer. Check both first.

## Agentic CI/CD in 2026 means agents beside the pipeline, not in charge of it

In practice, "agentic CI/CD" covers three different things, and you should keep them apart. The first is an **interactive agent with tool access to your CI and cluster**: Copilot agent mode in VS Code calls MCP servers to read build logs, pod events and Argo CD app state, and a person reads the answer. The second is a **headless agent CLI running as a pipeline step**: `copilot -p`, `claude -p` or `codex exec` runs non-interactively, takes logs or diffs as input and returns structured output. All three CLIs document this mode, and none of them needs GitHub Actions ([Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-with-actions); [Claude Code](https://code.claude.com/docs/en/headless); [Codex](https://learn.chatgpt.com/docs/non-interactive-mode)). The third is **vendor-native agent features** inside a single platform: Rovo Dev Agentic Pipelines can autonomously fix a failed step and push to the branch on Bitbucket Cloud ([Atlassian](https://support.atlassian.com/rovo/docs/work-with-rovo-dev-in-bitbucket-pipelines/)), and TeamCity's AI Build Analyzer gives "a summary, root cause, and possible fixes" from a log ([JetBrains](https://blog.jetbrains.com/teamcity/2025/10/livestream-recording-maximizing-teamcity/)).

Across all three, the consensus design is that **deterministic tools gate and AI advises**. Rendering, schema checks, policy checks and diffs stay deterministic: `kustomize build`, kubeconform, kube-linter, conftest or Kyverno, and `argocd app diff`. The model explains risk on top of those results. An August 2026 preprint makes the point sharply for GitOps edits. When models produced unified diffs, only **1.2 to 3.6% were correct**, and GNU patch silently misapplied **14 to 20%** of the diffs it accepted. When the model instead emitted a structured field change and code made the edit, the result was **100% correct with zero collateral changes over 415 runs** ([Davineni, alphaXiv 2609.00227](https://www.alphaxiv.org/abs/2609.00227.md)). It is a single, non-peer-reviewed paper, but it fits the incident record. Agents should propose an intent, a tool such as `kustomize edit set image` should make the edit, and a person should merge it.

## GitHub's flagship agents stop at the GitHub boundary; your stack has its own hooks

The Copilot coding agent "only works with repositories hosted on GitHub" ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). gh-aw compiles Markdown workflows into GitHub Actions ([GitHub Docs](https://docs.github.com/en/actions/tutorials/develop-agentic-workflows-in-github-actions)). Mirroring Bitbucket to GitHub to use them creates a second source of truth, so don't. Copy gh-aw's design instead: one Markdown task file per workflow, declared tools, read-only by default, a pinned engine version. Each such file becomes a TeamCity build configuration that runs Copilot CLI.

**Copilot CLI is the right headless engine for you**, because the same custom agents and instructions work in VS Code, in the CLI and in CI. It authenticates in CI through `COPILOT_GITHUB_TOKEN` holding a fine-grained PAT with the "Copilot Requests" permission. That PAT must be owned by a personal account, not an organization, and classic `ghp_` tokens are not supported ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)). That has two consequences. A CI job consumes one person's Copilot seat, or a bot user's seat. And since 2026-06-01 every run spends usage-based GitHub AI Credits ([GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)). GitHub's documentation covers only Actions, and no GitHub text found either permits or forbids running the CLI on TeamCity. Treat that as an open question for your GitHub admin.

The rest of the stack has these agent interfaces:

| Component | Agent surface | Read-only control | Status |
|---|---|---|---|
| TeamCity 2026.1+ | Built-in MCP at `<server>/app/mcp`; `teamcity` CLI with an agent skill | MCP "safe mode" by default: reads, plus triggering personal builds only. Brave mode is off unless `teamcity.ai.mcp.braveMode.enabled=true`. CLI honours `TEAMCITY_RO=1` | Official ([JetBrains Help](https://www.jetbrains.com/help/teamcity/2026.2/ai-agent-integration.html)) |
| TeamCity older than 2026.1 | Daghis/teamcity-mcp (87 tools; 31 in its safe dev mode) or raw REST | Dev mode | Maintenance-only since June 2026 ([GitHub](https://github.com/Daghis/teamcity-mcp)) |
| Bitbucket Cloud | Rovo Dev Code Reviewer, Agentic Pipelines, Rovo MCP Server | Tool-level; MCP includes PR merge | GA; tied to Bitbucket Pipelines and Atlassian Cloud ([Atlassian](https://www.atlassian.com/blog/bitbucket/the-atlassian-rovo-mcp-server-now-supports-bitbucket-cloud)) |
| Bitbucket Data Center | MCP plugin at `/rest/mcp/1.0/`, plus REST and Code Insights | Admin allowlists exposed endpoints in `mcp-tools.json` | Released 2026-09-29; bundled in 10.5, Marketplace for 9.x/10.x ([Atlassian Community](https://community.developer.atlassian.com/t/mcp-for-bitbucket-dc-has-been-released/102963)) |
| OpenShift | `containers/kubernetes-mcp-server` (Windows binary, reads kubeconfig) | `read_only = true`, `disabled_tools`, `denied_resources` | Upstream of Red Hat's Tech Preview OpenShift MCP server ([GitHub](https://github.com/containers/kubernetes-mcp-server/blob/main/docs/configuration.md)) |
| Argo CD | `argoproj-labs/mcp-for-argocd` (`npx argocd-mcp`) | `MCP_READ_ONLY=true` removes create, update, delete, sync and actions | Community, maintained by Akuity engineers ([GitHub](https://github.com/argoproj-labs/mcp-for-argocd)) |
| Vault | `hashicorp/vault-mcp-server` | None documented | Beta, "intended for local use only". **Do not install** ([HashiCorp](https://developer.hashicorp.com/vault/docs/mcp-server/overview)) |

Two caveats change how you use this table. First, the Bitbucket edition decides which row applies. Rovo Dev review and Agentic Pipelines are Cloud-only, and Data Center has no native AI review as of September 2026 ([DEV Community](https://dev.to/emilreiter/ai-code-review-on-bitbucket-data-center-whats-native-what-isnt-2b7j)). A self-managed TeamCity Enterprise shop is probably on Data Center. Even on Cloud, Agentic Pipelines run in Bitbucket Pipelines, not TeamCity. Second, a Code Insights report only displays: **"Posting a failed report will not stop a pull request from being merged"** ([Atlassian Developer](https://developer.atlassian.com/server/bitbucket/how-tos/code-insights/)). To gate merges you need a required-build merge check.

OpenShift Lightspeed is worth asking about. It is a GA console assistant that runs cluster actions through the same Kubernetes MCP server, with human approval for writes since 1.1, and it can use Azure OpenAI or a self-hosted model ([Red Hat](https://docs.redhat.com/en/documentation/red_hat_openshift_lightspeed/1.0/html-single/release_notes/index)). If it is already approved, it is a sanctioned fallback for when Copilot may not see cluster data. Bridging it into Copilot through `ols-mcp` is an unsupported proof of concept ([Red Hat Developer](https://developers.redhat.com/articles/2026/02/04/how-connect-openshift-lightspeed-mcp-your-ide)). Among AI SRE tools, k8sgpt runs its analyzers locally and sends only anonymized explanations to the LLM ([GitHub](https://github.com/k8sgpt-ai/k8sgpt)). That makes it a good deterministic first step an agent can call. Akuity Intelligence needs Akuity's SaaS platform and does not apply to OpenShift GitOps ([Akuity](https://akuity.io/blog/akuity-ai-software-delivery)). The research found no agent integrations for Podman/Buildah, Quay, DASY, Sonar or Sonatype. Treat their build output and scan reports as extra context for the triage agent, not as separate integrations.

## Every public exploit chained untrusted text, credentials and an exit

The incident record is consistent. In **CVE-2025-53773**, an injected instruction got Copilot to write `"chat.tools.autoApprove": true` into `.vscode/settings.json`, which disabled confirmations and gave remote code execution ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2025-53773)). **CamoLeak** hid prompts in PR markdown comments and leaked secrets through GitHub's own image proxy ([The Register](https://assets.theregister.com/2025/10/09/github_copilot_chat_vulnerability/)). The **Nx "s1ngularity"** npm malware ran installed AI CLIs with their safety flags off and had them hunt for tokens ([StepSecurity](https://www.stepsecurity.io/blog/supply-chain-security-alert-popular-nx-build-system-package-compromised-with-data-stealing-malware)). **Clinejection** turned an issue title into an `npm install` from an attacker's fork, then into cache poisoning, then into a malicious release ([Snyk](https://snyk.io/blog/cline-supply-chain-attack-prompt-injection-github-actions/)). In April 2026, **"Comment and Control"** hijacked agents from Anthropic, Google and GitHub through PR titles and hidden HTML comments. It bypassed the Copilot agent's firewall and secret scanning, and GitHub called the root cause "a known architectural limitation" ([SecurityWeek](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/)). None of these incidents involved TeamCity, Bitbucket or OpenShift. The vectors carry over anyway: Bitbucket PR text, TeamCity build logs and `oc logs` output all contain text an attacker can control.

The design rule that follows is Meta's **Agents Rule of Two**. In any one session, an agent may have at most two of three properties: it processes untrusted input, it has access to sensitive systems, or it can change state or communicate externally. If it needs all three, a human approves ([Willison](https://simonw.substack.com/p/new-prompt-injection-papers-agents)). Your triage and incident agents read untrusted logs and touch sensitive systems, so they get no write or egress capability. Your GitOps-change agent writes, so it must not read raw logs in the same session. In a Copilot handoff graph, the handoff from diagnose to implement is that boundary, as long as it passes a summary a human has reviewed rather than raw log text.

Each of your four guardrails maps to a server-side control backed by a client-side one:

| Guardrail | Client-side (Copilot) | Server-side (the real boundary) |
|---|---|---|
| No cluster mutations | `--deny-tool='shell(oc apply)'` and the same for delete, patch, scale, rollout, edit, exec, rsh, set and create, plus the `kubectl` equivalents and `argocd app sync/rollback/delete/set`; matching deny rules in `chat.tools.terminal.autoApprove`; kubernetes-mcp-server with `read_only = true` and `pods_exec`/`pods_run` disabled | A dedicated agent kubeconfig whose identity is bound to `view`, which excludes Secrets ([Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)); an Argo CD local account with `role:readonly` and no `sync` or `exec` ([Argo CD RBAC](https://argo-cd.readthedocs.io/en/stable/operator-manual/rbac/)) |
| No Vault access | Never register the Vault MCP server; deny `shell(vault:*)`, `oc get secret`, `oc extract`; set `denied_resources` for Secret in the Kubernetes MCP config | No `VAULT_TOKEN` or `~/.vault-token` in any shell the agent uses |
| No git push or merge | `--deny-tool='shell(git push)'` and `shell(git merge)` | Bitbucket branch permissions; Data Center `mcp-tools.json` without merge endpoints; agent tokens that cannot merge |
| No PROD overlay edits | Deny `write(**/overlays/prod/**)`; set `chat.tools.edits.autoApprove` to false for the prod overlays | Branch and path restrictions, required reviewers, and a CI check that fails when a prod overlay changes without approval |

Copilot CLI documents that **deny rules beat every allow**, including `--allow-all` and saved approvals ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools)). Even so, client-side deny lists are pattern matches, and three things about them are fragile. Denying `oc delete` may not catch `oc -n x delete`, or a script the agent writes and then runs. VS Code itself admits to "known limitations with shell aliases, quote concatenation, and complex shell syntax". And the terminal sandbox is only **Experimental on Windows** ([VS Code](https://code.visualstudio.com/docs/copilot/security)). Three gaps need specific fixes:

- **Copilot content exclusion does not apply to agent or edit mode** ([GitHub Docs](https://docs.github.com/en/copilot/concepts/context/content-exclusion)). Secrets must simply not be in the workspace.
- **`oc login` writes your admin token into the kubeconfig the MCP server reads.** Set a separate `KUBECONFIG` path in the MCP server's environment so the agent never inherits your session.
- **The agent can edit its own guardrails.** That is the CVE-2025-53773 class. Set manual approval for edits to `.vscode/settings.json`, `.github/**`, `*.instructions.md` and `*.agent.md`.

Never run with `--yolo` or `--allow-all`. In TeamCity, the agent's token should be read-scoped, and any posting to Bitbucket should happen in a separate deterministic step that takes the agent's JSON output. That way the agent process itself has no egress.

## A four-phase roadmap that never hands the agent a PROD write credential

The order below gives value in the first weeks and widens permissions only where you can explain why. Each phase lines up with one of your candidate workflow graphs.

| Phase | Build | Engine | Agent write access |
|---|---|---|---|
| 0. Verify (week 1) | Answer the checks in the next section; agree MCP and CLI policy with the Copilot admin | None | None |
| 1. Read-only copilots (weeks 1–4) | **TeamCity failure triage** and **OpenShift/Argo CD incident** graphs as VS Code custom agents. MCP: TeamCity `/app/mcp` in safe mode (or the `teamcity` CLI with `TEAMCITY_RO=1`), kubernetes-mcp-server read-only, argocd-mcp read-only. Optionally add k8sgpt `analyze` as a deterministic first step | Copilot agent mode | None |
| 2. Deterministic GitOps gates (in parallel) | A TeamCity build on GitOps PRs: `kustomize build` for every overlay, kubeconform with OpenShift CRD schemas, kube-linter, conftest or Kyverno (no `:latest`, registry allowlist, no inline Secrets, a prod-overlay check), and `argocd app diff`. Make it a required merge check | TeamCity | None; these block merges |
| 3. Headless agent in TeamCity | Run triage on build failure, including Podman/Buildah, Sonar and Sonatype output. A **GitOps PR reviewer** reads the rendered diff and writes Code Insights annotations. Both use `copilot -p --no-ask-user` with a narrow `--allow-tool` list, a full `--deny-tool` list and a pinned CLI version | Copilot CLI | None. A separate step posts the JSON result |
| 4. Agent-proposed changes | The **GitOps overlay change** graph (plan, implement, review): image-tag bumps through `kustomize edit set image`, on `agent/*` branches only, with your confirmation before any push and a human merge. Treat Kotlin DSL changes to TeamCity configuration the same way, once that configuration is in VCS | VS Code handoffs | Branch-only, confirmed each time |

Phase 1 needs no CI changes and no shared credentials, which makes it the cheapest way to learn where agents help on your stack. The TeamCity MCP safe mode already matches your guardrails: reads are free, and the only trigger allowed is a personal build ([JetBrains Help](https://www.jetbrains.com/help/teamcity/2026.2/ai-agent-integration.html)). Phase 2 matters more than anything AI-related in this plan. The deterministic gates are what make it safe to accept agent-authored PRs later, and the AI reviewer in phase 3 only explains what they found. The move to Kotlin DSL helps here: once build configuration is code in a repo, agents can propose changes to it through the same branch, review and merge path as the GitOps repo. No JetBrains feature that generates Kotlin DSL with AI was found, so the agent drafts and TeamCity's own DSL compilation validates. Leave the "feature to Bitbucket PR" graph until last. It needs push rights, so every run hits your push-confirmation rule.

## Spec Kit is overkill for two SPFx solutions, except for the upgrade

Spec Kit is healthy and fast-moving. Version **v1.1.1 shipped on 2026-10-06**, after five releases in two weeks ([releases](https://github.com/github/spec-kit/releases)). It now installs Copilot skills under `.github/skills/` and has a lighter bug-fix entry point ([README](https://github.com/github/spec-kit)). The evidence still says it costs more than it returns on routine web-part work:

- **Spec Kit's own contributors** use SDD for substantial features and let "small fixes use the normal issue and PR process" ([agentic-sdlc guide](https://github.com/github/spec-kit/blob/main/docs/guides/agentic-sdlc.md)).
- **Thoughtworks' Birgitta Böckeler** called it "overkill for the size of the problem" on a 3 to 5 point story ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
- **Scott Logic measured** about **3.5 hours of human review** and 2,577 lines of Markdown for 689 lines of code, against roughly 32 minutes iterating with the agent directly ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)).

Both reviews used 2025 versions. Under credit-based billing, every phase that re-reads the spec, plan and tasks also costs money.

The better fit is Microsoft's official, preview **SPFx development agent skill**, installed into `.github/skills/spfx/`. It detects the SPFx version, picks Heft (1.22 and later) or gulp (1.21.1 and earlier), runs Yeoman non-interactively, and defaults to PnPjs with bounded queries ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/dev/spfx/agent-skills)). Those are exactly the mistakes agents make on SPFx. Add a short repo `*.instructions.md` that covers four things:

- the exact SPFx and Node versions (Node 22 for 1.21 to 1.23) ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/dev/spfx/compatibility));
- React pinned with `--save-exact`;
- your internal UI library's conventions, which no public skill covers;
- a ban on App Catalog deploy commands.

For medium changes, use VS Code's built-in Plan agent, whose own docs say "For small, well-defined edits, direct implementation is more efficient" ([VS Code](https://code.visualstudio.com/docs/copilot/agents/planning)). Keep Spec Kit for one job: the coming upgrade. SPFx 1.24 brings React 18 and is targeted for October 2026, and 1.25 replaces Yeoman with the SPFx CLI ([Microsoft 365 Dev blog](https://devblogs.microsoft.com/microsoft365dev/sharepoint-framework-spfx-roadmap-update-august-2026/)). That is a cross-cutting, risky change where a written spec pays off. If you keep Spec Kit installed, pin the version, because its prompts change every few days.

## Conclusion

The available tooling decides less here than the shape of your permissions. Everything an agent can safely do on this stack today, it does through read-only identities, deterministic gates and branch-only proposals. All of that is configured in OpenShift RBAC, Argo CD RBAC, Bitbucket branch permissions and TeamCity's safe mode, none of which an injected prompt can change. That makes the Bitbucket and TeamCity setup an advantage rather than a gap. The GitHub-native agents that teams envy were the ones hit by every major 2025 to 2026 exploit. Building with plain glue forces the separation between agent and credential that those teams later had to retrofit.

The decision that matters most is not which agent to use but where the agent's output lands. Output that lands in your chat or a Code Insights report is cheap and reversible. Output that lands on a branch needs your confirmation and the phase-2 gates. Output that lands on a cluster stays a human action. If the phase-3 jobs prove reliable, the next step is not to give agents more write access. It is to make the deterministic gates strict enough that an agent-authored PR needs only one human look.
